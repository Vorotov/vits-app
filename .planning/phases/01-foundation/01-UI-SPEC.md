# Phase 1 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.
>
> **Scope note:** Phase 1 delivers ONLY the three-tab app shell (Stack / Calendar / Settings), stub screen headers, theme/token wiring, and layout rules — per ROADMAP.md and 01-CONTEXT.md. No feature screens, CTAs, lists, or data-bound states exist yet; those arrive in Phases 2–5. This contract is scoped accordingly and marks out-of-scope rows "not applicable in Phase 1."

## Typography

Phase 1 uses three of the four roles (tab label, stub-screen heading, and a caption/body role for any subtitle text). Display is unused until Phase 3 (progress-ring counters, etc.) but is declared now for token completeness.

| Role | Size | Weight | Line Height | Font | Notes |
|------|------|--------|-------------|------|-------|
| Label (tab label) | 10px | 500 | 1.0 | Instrument Sans | Bottom NavigationBar destination labels |
| Body (caption/subtitle) | 13px | 400 | 1.4 | Instrument Sans | Reserved for stub-screen subtitle text if any is added; color `textMuted` |
| Heading (stub screen title) | 25px | 600 | 1.1 | Instrument Sans | Letter-spacing **−0.5px** (mockup: `-.02em` on 25px ≈ −0.5px). This is the "mockup header style" referenced in 01-CONTEXT.md for stub screen headers. |
| Display | — | — | — | — | Not used in Phase 1 — reserved for large numeric displays (e.g. dose-progress ring counter) starting Phase 3 |

Mono numerals rule (for later phases building on this shell): any numeric/counter/timestamp text uses JetBrains Mono with `font-feature-settings: 'tnum'` equivalent (tabular figures) — not applicable to any Phase 1 screen since no numerals render yet, but the font is bundled now so this rule is ready to use.

**Font-weight exception (locked, exempt from the 2-weight guideline):** the GSD default guideline caps typography at 2 declared font weights. This project's mockup uses three Instrument Sans weights — 400 (body/caption), 500 (nav labels), and 600 (headings) — sourced from `claude_design_mockup/VitoMy v0.1.dc.html` and locked as-is in 01-CONTEXT.md. This is a deliberate, user-locked deviation from the 2-weight guideline: the mockup's design system genuinely differentiates nav labels (500) from headings (600) and body text (400), and none of the three values may be collapsed or substituted. Do not reduce to two weights in implementation.

## UI Considerations

Probe run 2026-08-14 over elements E1 (NavigationBar) and E2 (stub screens): 14 applicable, 13 resolved explicit, 1 resolved backstop, 0 unresolved.

**Resolved — explicit truths (planner lifts each into `must_haves.truths`):**

- E1 empty/loading/error: the NavigationBar is static — it always renders exactly three destinations synchronously on first frame, independent of any data, with no loading or error state (no async source exists in Phase 1).
- E1 populated: normal state is three destinations, each icon + localized label; exactly one selected in accent #4A4E7C, unselected in #A0A0A9, bar background surfaceAlt #FBFBF9 with 1px hairline top border.
- E1 overflow: `flutter test` widget test in uk locale produces no RenderFlex overflow errors for the NavigationBar (longest label "Налаштування").
- E2 empty: the stub screens ARE the designed empty state for Phase 1 — heading text only on paper background; no empty-state copy exists by design (content states arrive in Phases 2–4).
- E2 loading/error/partial: stub screens render no async or partial data — heading renders synchronously; no loading, error, or partial states exist in Phase 1.
- E2 populated: populated state equals the heading (25px/600, sole focal anchor); nothing else renders.
- E2 zero-one-many: no item collections exist on Phase 1 screens; zero/one/many layouts are out of scope until Phase 2.
- E2 overflow/long-text: headings sit in containers with no fixed width (EdgeInsetsDirectional padding only) and are allowed to wrap; `flutter test` in uk and en locales produces no overflow exceptions on any stub screen.

**Resolved — backstop (planner lifts as `{ statement, verification: backstop }`):**

- statement: uk NavigationBar labels (15–25% longer than en) never truncate or clip inside the ~66px destination column at 10px/500 — use `FittedBox(fit: BoxFit.scaleDown)` on the label `Text`; verified visually in uk locale on a simulator before phase sign-off.
  verification: backstop

**Additional covered rules (from CONTEXT.md, apply project-wide from this phase on):** no fixed-width text containers; EdgeInsetsDirectional for all horizontal padding (direction-agnostic layout, RTL forward-proofing).

## Layout & i18n Rules

- Use `EdgeInsetsDirectional` (not `EdgeInsets`) for all horizontal padding in `AppShell` and stub screens — locked in 01-CONTEXT.md.
- No fixed-width containers around any `Text` widget — locked in 01-CONTEXT.md; uk strings run 15–25% longer than their en counterparts and must never be clipped.
- NavigationBar destination labels must use `FittedBox(fit: BoxFit.scaleDown)` (or equivalent shrink-to-fit) rather than truncation, per the UI Considerations row above.
- Tab bar theming maps directly onto Flutter's `NavigationBar`/`NavigationBarThemeData`:
  - `backgroundColor`: surfaceAlt `#FBFBF9`
  - Selected destination icon + label color: accent `#4A4E7C`
  - Unselected destination icon + label color: textFaint `#A0A0A9`
  - Indicator: Material 3 default (no custom indicator color specified by the mockup; leave as theme default or `Colors.transparent` if the mockup's flat two-state look — no pill indicator visible in the mockup nav bar — is preferred; Claude's Discretion, note choice in implementation)
  - Elevation/shadow: none visible in mockup (flat `1px` top border `rgba(23,23,27,.08)` only) — set `elevation: 0` and add a top `Border` or `Divider` in that color instead of relying on Material elevation shadow
