# Phase 7 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

> **Scope note — this phase draws almost nothing.** Phase 7 ships **zero new screens, zero new widgets, zero new tokens and zero new in-app copy**. Its entire user-visible surface is (a) text the **operating system** renders on a lock screen, (b) a permission dialog the **operating system** owns, (c) one row in **Android's own** notification settings, and (d) a change to which tab is selected. The only thing this phase adds to the Flutter tree is an app-lifetime tab-index notifier that replaces `_AppShellState._selectedIndex` (`app_shell.dart:29`) — geometry-neutral, pixel-neutral.
>
> **Authoritative sources:** `docs/superpowers/specs/2026-08-17-boostque-v1.1-design.md` §2 (approved architecture — locked, not re-opened) and `.planning/phases/07-dose-reminders/07-RESEARCH.md` (verified, executed research — trusted). House style and structure follow `.planning/phases/06-shell-simplification/06-UI-SPEC.md`.
>
> **Precedence rule used throughout:** where the spec and 07-RESEARCH.md conflict on a *code fact*, **research wins**. Where **both** are contradicted by the shipped 22.3.0 source read for this contract, the **source wins** and the divergence is recorded in § 10. Exactly one such correction exists (§ 10 / DECIDED-14): the Android channel **name and description are mutable**, so research Pitfall 8 / Q-2 is wrong and its recommended remedy (version the channel id to relocalize) would be actively harmful.
>
> **Consumption rule:** the design system is ESTABLISHED (Phases 1-6). Nothing in this phase renders a pixel through it. The tokens, spacing scale and typography sections below are therefore **statements of absence**, and their absence is checkable.
>
> **Discretion resolved:** research left five open questions (Q-1..Q-5). The two with a user-visible surface — **Q-1** (tail sentinel notification) and **Q-2** (channel name localization) — are DECIDED here (DECIDED-9, DECIDED-14) and the planner must not treat them as open. Q-3/Q-4/Q-5 are engineering questions with no visual surface and are left to the planner.

## 2. Notification content — the copy contract

This is the crux of the phase. Everything below is **locked ARB copy**, not a suggestion.

**Two absolute prohibitions, both security controls, not style preferences** (spec §2.1, 07-RESEARCH § Security Domain V4):

1. **No supplement name may reach `title`, `body` or `payload`.** Supplement names are health-adjacent data and these fields sit on a lock screen. iOS exposes no `hiddenPreviewsBodyPlaceholder` through this plugin, so **body content is the only privacy control available**. This is why the count-only body is a control and not a copy choice.
2. **`notification_service.dart` must not be able to learn a supplement name.** It reads `regimensStreamProvider`, never `stackEntriesProvider` or `SupplementRepository` (07-RESEARCH §8.3 explicitly notes the latter is needed "only if notification copy ever names a supplement (it does not)"). A capability that does not exist cannot leak.

### 2.1 DECIDED-1 — Title AND body, and the title is constant

The notification has **both** a title and a body. The title is a **fixed string with no placeholders**: uk «Час прийому» · en "Time for your doses".

Rationale:

- **The title must not carry the app name.** Both platforms already print it in chrome the app does not control — Android in the notification header row, iOS in the banner header. A title reading "Boostque" would spend the most valuable line in the notification restating the one fact the OS has already stated for free.
- **The title must not carry the count or the time either.** Both are variable, and a title that changes on every delivery loses the thing a title is for: instant, pre-reading recognition. With a constant title, three stacked reminders read as one family of the same kind of thing, and the differences sit exactly where the eye goes second.
- **Body-only was rejected.** A title-less notification renders the body in the title slot on both platforms, which works — but it throws away a free line and it makes the *variable* text the recognition line, which is the inversion of the point above. iOS also truncates the title more aggressively than the body, so putting the numerals there is the wrong trade.
- **Title-only was rejected** for the same reason in reverse: it forces count + time into a line that truncates first.

### 2.2 DECIDED-2 — Body = time, then count

Body: `{time} · {count doses}` → uk «08:00 · 3 прийоми» · en "08:00 · 3 doses".

- **Time first** because it is the disambiguator: it answers "*which* reminder is this?", which is the question a user asks before "how many?".
- **The ` · ` separator is the house idiom**, taken verbatim from `doseSheetSubtitle` («{time} · {dose}», `app_uk.arb:114`) and `stackSummary`. It is also the reason there is no preposition: Ukrainian requires «о 08:00» but «об 11:00» — an hour-dependent inflection that ICU cannot express and that a `plural`-on-hours hack would encode as a lie. The separator sidesteps it entirely, and it is what the app already does.
- **Word order is the translator's, not the code's.** Both fragments live inside one ARB value, so an RTL or verb-final locale can reorder freely without a code change. No sentence in this phase is composed from concatenated localized fragments.

### 2.3 DECIDED-3 — The time IS restated, in 24-hour `HH:mm`

⚖️ **Judgement call.** The notification arrives *at* the time, so restating it looks redundant. It is restated anyway. Three reasons, in increasing weight:

1. **Delivery ≠ schedule.** `AndroidScheduleMode.inexactAllowWhileIdle` is a locked decision with an accepted ~10-15 min doze jitter (spec §2.2). The OS chrome timestamps the notification with its **delivery** time, which under jitter is not the dose time. Without the scheduled time in the body, the app has printed a number that is quietly wrong about the only thing the reminder is about.
2. **Reminders queue.** A user who unlocks at 19:00 can see the 08:00, 13:00 and 18:00 reminders at once. The chrome distinguishes them by delivery time; the counts may coincide. The scheduled time is the only field that identifies *which dose group* each one is.
3. **Adjacent slots exist.** A stack with slots at 08:00 and 08:30 makes 15 minutes of jitter genuinely ambiguous. The body resolves it.

Format is **24-hour `HH:mm`, zero-padded**, produced by `DateFormat.Hm(localeName)`. This is the non-`BuildContext` equivalent of the app's universal `MaterialLocalizations.formatTimeOfDay(tod, alwaysUse24HourFormat: true)` (`day_block_section.dart:73`, `dose_action_sheet.dart:48`, `regimen_editor_screen.dart:628`): the `Hm` skeleton is 24-hour by definition in every locale, so the notification can never disagree with an in-app time display.

### 2.4 DECIDED-4 — The count counts DOSES

`count` is **the number of doses due at that one time-of-day**. Not supplements in the stack, not doses remaining in the day, not slots in the schedule.

- The chosen word follows: uk «прийом» (the act of taking, consistent with the existing `scheduleTitle` «Розклад прийому» and `ringSemantics` «…доз прийнято»); en "dose" (consistent with `doseLabel` "Dose", `emptyDayTitle` "No doses on this day", `ringSemantics` "…doses taken"). The spec's own example text — "3 прийоми" — is honoured verbatim.
- Because one regimen exists per supplement (the PF-8 collapse, `repositories.dart:135`) and slots within a regimen carry distinct `minutesFromMidnight`, the dose count at a time-of-day numerically equals the number of supplements due then. **That coincidence must not be used to justify the word "supplements".** The user's action is a taking, the notification asks for a taking, and if the data model ever admits two doses of one supplement at one minute the copy stays true.
- **`count == 0` is impossible by construction:** the pure plan emits no `PlannedNotification` for a time with no active doses. There is no zero-state copy, and there must not be one.

### 2.5 DECIDED-5 — `time` is a pre-formatted `String` placeholder

⚖️ **Judgement call.** The ARB placeholder is `{ "type": "String" }`, formatted by the notification service, **not** `{ "type": "DateTime", "format": "Hm" }`.

- gen-l10n supports the `DateTime`/`Hm` form and it would be the more orthodox i18n shape — a locale could then choose its own time pattern. **That freedom is precisely what this app has already refused:** every in-app time is forced to 24-hour by `alwaysUse24HourFormat: true`, and a per-locale `format` directive in an ARB file would let a future translator introduce a 12-hour clock in the notification that disagrees with every clock inside the app, silently, with no test able to see the intent.
- Keeping the format in one named Dart helper puts the app's locked 24-hour rule in exactly one place, unit-testable without a widget, and avoids introducing the ARB's first `type: DateTime` placeholder (there are none today — verified).
- Recorded alternative, for a future reader who wants it: switch `time` to `{"type": "DateTime", "format": "Hm"}` and delete the helper. Do it only if the 24-hour house rule is being relaxed app-wide.

### 2.6 DECIDED-6 — Ukrainian plural forms

Ukrainian carries **all four CLDR forms** (`one` / `few` / `many` / `other`), following `substancesCount` (`app_uk.arb:10`) exactly. English carries `one` / `other`.

`other` is **unreachable for an `int`** in Ukrainian — CLDR routes every integer to `one`, `few` or `many`, and `other` only ever matches a decimal. gen-l10n requires it regardless. This contract mirrors the `few` form into `other`, which is what 5 of the 7 existing plural keys in `app_uk.arb` do (`substancesCount`, `weeksCount`, `stackSummary`, `monthsCount`, `periodsCount`). The linguistically-strict alternative (genitive singular «прийому», as `slotsPerDay` uses) is equally correct and equally unobservable; house consistency decides it.

## 3. The permission moment

### DECIDED-7 — Nothing of ours precedes the OS dialog. ⚖️ Judgement call, against research's recommendation.

07-RESEARCH §6.3 recommends "a short pre-prompt sheet before the system dialog… worth it given there is no retry". **This contract declines it.** The reasoning research did not carry:

- **A pre-prompt's whole value is deferral** — it lets the user say "not now" without burning the one iOS prompt that exists for the app's lifetime. **Deferral requires a later ask, and the later ask is explicitly deferred** (spec §2.6 puts the re-ask path in the deferred settings screen). A pre-prompt whose "Not now" is *permanent and unrecoverable* is strictly worse than the system dialog: identical outcome, one extra tap, plus a persisted "declined our sheet" bit, plus a new modal to lay out, localize, size at textScaler 2.0 and test — in a phase that otherwise adds no UI.
- It would be the app's **first modal that interrupts a save confirmation**. The regimen editor's only existing dialog is the delete-confirmation gate, which is a destructive-action guard. Reusing that weight for a housekeeping request devalues it.
- **The priming is done with sequencing instead of copy.** The dialog lands immediately after the user has saved a dosing schedule with times in it — the single most self-explanatory context an OS notification prompt can appear in. That is the cheapest possible priming and it costs no surface.

**Cost accepted and stated plainly:** a reflexive "Don't Allow" on iOS is unrecoverable inside the app until the deferred settings screen ships. This is a real regression risk against grant rate, it is knowingly taken, and § 4 records what the deferred screen must carry to close it.

> **Correction to the stated ground, recorded 2026-08-17 during plan 07-05 (07-UI-CHECK FLAG-1). The DECISION is unchanged: no priming sheet, the operating system's dialog is still shown bare.**
>
> The first bullet above over-generalises. It rejects a primer on the ground that a primer's whole value is deferral and there is no later ask to defer to — which is true of a primer offering a **"Not now"**, and only of that shape. It is **not** true of the other standard shape, a **continue-only** primer, which defers nothing and exists purely to supply context before an irreversible choice. This contract never evaluated that shape, so "identical outcome, one extra tap" was asserted about a design it did not consider. A continue-only primer might well raise the grant rate.
>
> The continue-only shape is declined anyway, on the two grounds that do survive the correction plus one that now exists:
>
> 1. **The sequencing already supplies the strongest context available.** The dialog lands the instant after the user has saved a dosing schedule full of times. No copy of the app's own can beat that, and it costs no surface.
> 2. **It would be the app's first modal interrupting a save confirmation**, in a phase that otherwise adds no interface — the second bullet above, which stands as written.
> 3. **The residual cost is now addressed by recovery rather than by persuasion.** DECIDED-9a's permission-state row and its route into the operating system's own settings answer the unrecoverable refusal directly, which is the cheaper and more honest half. Raising the grant rate at the prompt was never the only way to close that gap.
>
> The same correction is written at the ask itself, in `regimen_editor_screen.dart`, so a reader meets it where the decision is implemented as well as where it is stated.

### What the user actually sees at the save moment

Sequence, exactly:

1. User taps Save in the regimen editor. Existing behaviour, unchanged: `_saving` latches, `await controller.save()`, then `await Navigator.maybePop()` (`regimen_editor_screen.dart:960-998`).
2. The editor route pops. The user is back on the tab they came from, with the just-saved supplement visible in the list.
3. **Then** the OS permission dialog appears — over that screen, not over an exiting route. On Android 13+ this is the `POST_NOTIFICATIONS` rationale dialog; below 33 nothing appears at all (documented no-op, 07-RESEARCH §6.2). On iOS it is the one-and-only `UNUserNotificationCenter` prompt.
4. Whatever the user answers, the app looks identical afterwards. No snackbar, no toast, no banner, no badge, no state change on any screen.

**Ordering is a contract, not an implementation detail:** the request fires **after** `maybePop` resolves. A system dialog raised over a route mid-exit-transition is disorienting on both platforms and, on iOS, lands over a view that is being torn down.

### DECIDED-8 — Asked at most once per install

The ask is gated on a persisted boolean ("we have asked"), following the `app_locale` precedent for small non-domain state (`shared_preferences`, not Drift). Without it, Android re-shows the rationale dialog on **every** regimen save until the user has denied twice — which is exactly the nagging spec §2.5 forbids. Neither platform's API can distinguish "denied" from "never asked" (07-RESEARCH §6.1, §6.2), so the app must remember.

### Non-negotiables at this seam

- **The save is never blocked, delayed, or made to depend on the permission flow.** The write completes and the route pops before the request is even issued. The request's result gates nothing: no navigation, no rebuild, no user-visible branch.
- **A failure in the permission path is invisible to the user.** It is reported via `FlutterError.reportError` in the shape `main.dart:28-36` already establishes for the `SharedPreferences` bootstrap — a facility this codebase already treats as the correct home for "absorbed, not surfaced".
- **The ask is triggered by the save ACTION, never by state.** A provider that asks when "a regimen exists" would fire on every cold start for an existing user, which is the launch-time prompt NOTIF-03 forbids.

## 4. Silence, denial, and the honest limitation

Three ways this app can be quietly doing less than the user believes:

| Cause | Signal available to the app | User-visible in v1.1 |
|---|---|---|
| Permission denied (or later revoked in OS settings) | `areNotificationsEnabled()` / `checkPermissions()` — the app *can* detect this | **nothing** |
| Tier-B horizon lapsed (app unopened past the 30-day / 60-request bound; ~a week for a typical cycling stack) | derivable | **nothing** |
| Android force-stop or OEM battery killer | **no API detects either** (07-RESEARCH Pitfall 11) | nothing possible |

### DECIDED-9 — SUPERSEDED BY THE PROJECT OWNER, 2026-08-17

> **DECIDED-9a (owner decision, binding — overrides DECIDED-9 in part).**
>
> v1.1 **does** surface notification-permission state, in the existing Settings screen: one row
> stating whether reminders are allowed, plus a control that opens the OS notification settings.
>
> This was escalated because DECIDED-7 and DECIDED-9 compound into a path with no exit — a bare
> OS prompt, no in-app re-ask on iOS, and no indication anywhere that the feature is dead. One
> reflexive "Don't Allow" silently disables the whole phase, permanently, with no feedback. Each
> decision priced its own cost honestly; neither priced the composition (07-UI-CHECK FLAG-2).
>
> **What this adds, and only this:**
> - A permission-state row in `features/settings/`: allowed / not allowed, and an action calling
>   `openAppNotificationSettings()` — the only route back on iOS after a denial, and after a
>   double-denial on Android.
> - Two ARB key pairs (state label, action label) in both locales.
> - The row reads permission state, so the `grep` invariant below is amended: the primitives
>   become reachable from exactly ONE place under `lib/features/` — this row — and nowhere else.
>
> **What this does NOT add, and must not grow into:**
> - No magnitude, no numeral. The tier-B "roughly a week" sentence still belongs to the deferred
>   settings screen; the Phase-5 screen-scope invariant is respected in letter and spirit, because
>   a state row needs no number.
> - No on/off toggle, no per-slot choice, no quiet hours — still deferred (spec §2.6).
> - No priming sheet. DECIDED-7 stands unchanged: the OS dialog is still shown bare. The owner
>   chose recovery over persuasion, which is the cheaper and more honest half.
> - No tail sentinel notification. That half of DECIDED-9 stands, with its rationale intact.
>
> The tier-B horizon lapse therefore remains invisible in v1.1. That residual cost is accepted
> knowingly and stays on the deferred screen's hand-off list below.

### DECIDED-9 (original, retained for its reasoning) — v1.1 ships NO acknowledgement, and NO tail sentinel notification.

This is an explicit decision with a stated cost, not an omission. Spec §2.3 says the limitation is "to be stated in the UI when notification settings arrive"; settings do not arrive in v1.1.

**Why not a line in the existing Settings screen** (which does exist as a pushed route): §2.6 defers the *notification settings screen*, and a single static informational sentence is arguably not one — but the Phase-5 screen-scope invariant reaffirmed by 06-UI-SPEC states that `features/settings/` "contains no `risk`/`warn`/`calm` token, **no numeral**, no date, no free-text input, and no database write". An honest statement of this limitation wants a magnitude ("about a week", "30 days"), and a version stripped of magnitude ("reminders may stop if you don't open the app") is vague enough to alarm without informing. Adding a section also means new keys, new layout, new tests and a new state read on a screen this phase should not touch at all.

**Why not a tail sentinel notification** (07-RESEARCH Q-1, which *recommends* adding it):

- It converts a silent degradation into a **scheduled interruption whose only call to action is "open the app"** — and it targets precisely the users who have stopped opening the app, i.e. the ones least likely to act and most likely to read it as nagging. Spec §2.5's "no nagging" is a product stance, and this is the shape nagging takes when it is well-intentioned.
- It would post a **non-dose message on the `doses_v1` channel**, whose name and description promise dose reminders. On Android the user's only way to silence it is to silence dose reminders — the channel contract would be broken by the app that wrote it. A second channel just for housekeeping is more surface than the message is worth.
- It fires at an arbitrary boundary (30 days out, or wherever the 60-request budget binds) that corresponds to nothing in the user's own schedule.

**Cost accepted:** a denied permission and a lapsed tier-B horizon are both indistinguishable from working reminders, from inside the app, for the whole of v1.1.

**Zero-visual-difference invariant (checkable):** no widget, no screen and no ARB key reads or reflects notification permission state in v1.1. `grep -rn "areNotificationsEnabled\|checkPermissions\|requestPermissions\|requestNotificationsPermission" lib/features/` returns **nothing** — the permission primitives are reachable only from `lib/core/notifications/` and the one save call site.

### What the deferred settings screen MUST carry (hand-off, binding on whoever plans it)

1. **The tier-B limitation, with its magnitude** — that reminders for cycling regimens and courses are scheduled ahead only a limited distance and depend on the app being opened occasionally; roughly a week of silence for a typical stack before they lapse. This is the sentence spec §2.3 promised.
2. **Permission state, and the recovery path** — `checkPermissions()` / `areNotificationsEnabled()` plus `openAppNotificationSettings()`, which is the *only* route back on iOS after a denial and after a double-denial on Android. This is the debt DECIDED-7 knowingly took on.
3. On/off, per-slot vs daily-summary, quiet hours (spec §2.6).
4. **The Android OEM caveat** — force-stop and vendor battery managers can defer or block reminders with no API to detect it (07-RESEARCH Pitfall 11). Documentation-only for v1.1; the settings screen is where it becomes visible.

## 5. The tap destination

### 5.1 DECIDED-10 — Tap sets the tab to Сьогодні **and** resets the browsed day to today

Setting the tab index alone is a **bug**, not a partial implementation. `selectedDayProvider` holds "the day the user is browsing, or `null` to follow today", and its own doc records that "the shell keeps the Сьогодні screen mounted on every tab, so this never actually disposes while the app is running (WR-05) — the browsed day therefore survives a tab round trip" (`calendar_providers.dart:30-35`). A user who last browsed Monday and taps today's 08:00 reminder would land on **Monday's** dose list, with the reminder pointing at the wrong doses and the taken/not-taken state of a past day.

The tap handler therefore does exactly two things:

1. sets the tab index to **1** (Сьогодні — 0 Стек / 1 Сьогодні / 2 Календар, `app_shell.dart:10`), and
2. calls `selectedDayProvider.notifier.followToday()` (`calendar_providers.dart:27`).

And **nothing else**: no scroll-to-block, no row highlight, no sheet, no snackbar. The payload carries no time (DECIDED-13), so there is no scroll target even in principle. Cost accepted: with a long day the user may scroll to reach the block. Rationale: scrolling to a block is a new mechanism on the app's most-used screen, the day view groups into four coarse blocks that do not match the notification's exact-minute grouping (`day_view_model.dart:29-35`, and 07-RESEARCH §8.5 warns explicitly against reusing `blockIndexOf` here), and a reminder that jumps the view is harder to reason about than one that just shows today.

### 5.2 DECIDED-11 — The tap never pops a pushed route

If the user is inside the regimen editor, the add-supplement sheet, the dose action sheet or the pushed Settings route when a notification is tapped, the tab index changes **underneath** the route and the user keeps seeing the route. Nothing is popped.

Rationale: popping would discard an in-progress regimen edit because a reminder happened to fire. That is a destructive side effect triggered by a timer. Cost accepted and stated: the tab switch is invisible until the user pops the route themselves, at which point they land on Сьогодні — which is the correct destination, just later.

### 5.3 DECIDED-12 — Cold start: resolved before `runApp`, correct on frame 1

The `initialize()` callback cannot handle a launch-from-tap (07-RESEARCH §8.6, quoting the plugin's own doc comment), so `getNotificationAppLaunchDetails()` is read in the `main()` bootstrap window and **its answer seeds the tab notifier's initial value**, before `runApp`.

The user must **never** see Стек on frame 1 and then jump to Сьогодні. This is the exact pattern and the exact justification `LocaleController` already carries — "Synchronous seed: the stored override is applied on frame 1, so a user who set one never sees a system-language frame first (P-4 Option A)" (`locale_controller.dart:41-43`). The same shape applies: the launch details resolve in the same `main()` window as `SharedPreferences`, and with the same failure stance — a throw is caught, reported via `FlutterError.reportError`, and degrades to the default tab. **A notification tap must never be able to prevent the app from starting.**

The browsed-day reset of DECIDED-10 is free on cold start (`selectedDayProvider` builds `null` = follow today) but must still be expressed through the same single handler, so warm and cold paths cannot drift.

### 5.4 DECIDED-13 — Payload is one constant token, whitelisted

The payload is a single stable identifier naming the destination (`today`), defined as one `const` in `lib/core/notifications/`, and **validated by equality** on the way back in.

- It is **untrusted input** (07-RESEARCH § Security Domain V5): the OS persists it across app updates and can replay it. The same stance the codebase already takes for the stored locale tag (`locale_controller.dart`) applies — only a known value is honoured.
- **Anything else — a payload from an older build, a null, an unknown string — produces no tab change and no day reset.** The app opens on whatever it would have opened on. No error copy, no report to the user.
- Carrying no time in the payload is what makes the whitelist a single equality check, and it keeps a dose time out of a string the OS persists.

### 5.5 A tapped reminder may be stale — and the existing copy already covers it

A notification can outlive its cause: the supplement was deleted, the regimen paused, or the app was force-stopped so the cancel never ran. On arrival at Сьогодні the user then sees either fewer doses than the body promised, or none at all.

**No new copy is needed and none may be added.** The zero case renders the existing empty-day state (`emptyDayTitle` "No doses on this day" / `emptyDayBody`); the partial case renders a normal, shorter day. The count in the body is a **snapshot at scheduling time** and this contract states it as such rather than pretending otherwise. Chasing exactness here would mean a delivery-time hook, which neither platform offers for local notifications (spec §2.2 — "impossible, not merely worse").

## 6. The Android channel — UI copy the OS renders

The channel name and description are visible in **Android's own** Settings › Apps › Boostque › Notifications. They are user-visible copy and are localized like everything else.

### DECIDED-14 — Localized, refreshed on locale change, id NOT versioned. ⚖️ Corrects 07-RESEARCH Pitfall 8 / Q-2.

Research states the channel name "cannot be changed by an app update — only by a new channel id, which resets the user's own customization", and calls the locale-neutral-vs-first-run-locale choice a genuine open question. **The premise is false**, verified from the shipped source this session:

- `FlutterLocalNotificationsPlugin.java:2119-2125` — the Dart-facing `createNotificationChannel` method calls `setupNotificationChannel(...)` **unconditionally**. It does *not* pass through `canCreateNotificationChannel` (line 475), which is the gate that skips existing channels; that gate is only on the show/schedule path (line 270).
- `setupNotificationChannel` (line 1235) constructs a `NotificationChannel(id, name, importance)`, calls `setDescription(...)`, and hands it to `NotificationManager.createNotificationChannel(...)` (line 1288). Android's documented behaviour for an existing id is to **update the channel's name, description and group**; importance and per-channel behaviours the user has customized are preserved (an app can never raise importance after creation).

Therefore:

| Property | Value |
|---|---|
| Channel id | **`doses_v1`** — never re-versioned to relocalize. Versioning would create a *second* channel, orphan the user's own settings on the first, and is exactly the harm research's own recommendation would have caused |
| Name | `doseChannelName` — uk «Нагадування про прийом» · en "Dose reminders" |
| Description | `doseChannelDescription` — uk «Одне нагадування на кожен час прийому у вашому розкладі.» · en "One reminder for each dose time in your schedule." |
| When written | Explicitly at app start (the `main()` bootstrap window, alongside `initialize()` and `initTimeZones()`), **and again on every resolved-locale change** — the same trigger set as the reschedule (§ 7.2) |
| Importance | `Importance.high` on every call. Safe to repeat: Android ignores an attempt to raise importance on an existing channel, so a user who turned it down keeps their choice |

**Consequence for the executor:** research §5.5's `const _details` with the literal `'Dose reminders'` / `'Doses'` channel name **cannot ship**. `AndroidNotificationDetails` must be built per call from the same two ARB keys, so the name it carries can never disagree with the channel the app created. Its `channelAction` stays at the default `createIfNotExists`, so the schedule path never rewrites the channel behind the user's back — only the explicit startup/locale-change call does.

**The residual honest limit:** a *deleted* channel keeps its old name if Android restores it from its own tombstone before our next explicit create. Not worth handling; recorded so nobody hunts it.

## 7. l10n and accessibility mechanics

The usual widget rules — text scaler, `EdgeInsetsDirectional`, no fixed-width text container, `Semantics` with its own `onTap` — **do not apply to notification text at all**, because no widget renders it. What replaces them:

### 7.1 DECIDED-15 — Which locale the text is built in

The text is built with the top-level, **synchronous** `lookupAppLocalizations(Locale)` (`lib/core/l10n/gen/app_localizations.dart:1054`) — never through a `BuildContext`, which the scheduler does not and must not have (07-RESEARCH §8.5).

The `Locale` passed in is **the locale the UI is currently rendering in**, observed from the widget tree (via `Localizations.localeOf`) and published into an app-lifetime provider that the notification sync watches. It is **not**:

- the **device** locale — the user may have set a manual override (`localeControllerProvider`, `null` = follow system), and a notification in a language the app is not showing is a bug;
- **re-derived** by reproducing `MaterialApp`'s resolution algorithm. ⚖️ Judgement call: re-deriving it as `localeControllerProvider.state ?? basicLocaleListResolution(platformDispatcher.locales, AppLocalizations.supportedLocales)` is exactly what `MaterialApp` does today and would work — but it is a *second* copy of a resolution rule whose correctness depends on `main.dart` never passing a `localeResolutionCallback`. Observing the resolved locale is identical by construction. This is the same reasoning `planner_view_model.dart` records for having ONE activity decision point (the PF-1 defect class); a second copy of a resolution rule is the same shape of defect.

Because the app forces 24-hour time everywhere, the `time` fragment is formatted with `DateFormat.Hm(locale.toLanguageTag())` from the same locale — one helper, one place (§ 2.5).

### 7.2 DECIDED-16 — A language change MUST force a reschedule

**Yes — it is a hard contract, and it is not in the spec's trigger list** (spec §2.4 lists regimen created/edited/paused/resumed, supplement deleted, app resumed, midnight rollover; 07-RESEARCH Pitfall 7 / R-10 catches the gap).

A scheduled notification carries text **frozen at scheduling time**. A user who switches to English keeps Ukrainian banners for up to 30 days, silently, with nothing but a test able to notice. So `localeControllerProvider` — or, per DECIDED-15, the resolved-locale provider — joins the sync provider's watch set, and a locale change re-issues every scheduled notification with new text.

**The reconciliation trap the planner must handle:** notification ids are derived from `tier | hhmm | date` (07-RESEARCH §11) and **carry no locale**. A locale change therefore produces an *identical desired id set*, and a naive id-only set diff computes an empty diff and does nothing — the bug survives the fix. Two acceptable resolutions:

- **(a), recommended:** include the rendered `title` + `body` in the reconcile comparison. `pendingNotificationRequests()` returns `PendingNotificationRequest(id, title, body, payload)` (07-RESEARCH §5.6), so the currently-scheduled text is *readable* and stale text is detectable. This is self-correcting: it also repairs a reschedule that was interrupted mid-flight, and it needs no special-case trigger.
- **(b), acceptable:** treat a locale change as a distinguished trigger that forces a full cancel-and-reschedule of every desired id.

Either way, **never `cancelAll()`** — it also dismisses delivered-but-unacted reminders and leaves a window with nothing scheduled (07-RESEARCH §11).

### 7.3 DECIDED-17 — Already-delivered notifications are left alone

A notification sitting in the shade or Notification Center in the previous language is **not** rewritten, re-posted or recalled. It is a record of something that already happened, at a moment when that was the app's language. Re-posting it would either duplicate it or resurface a reminder the user has already read — a worse outcome than a stale string.

### 7.4 Accessibility, restated for an OS surface

- **Screen readers read the notification the OS built.** Title and body are read verbatim, which is why both must be self-contained sentences and why the count must be a word-bearing plural rather than a bare numeral — `«5 прийомів»` reads correctly; `«5»` does not.
- **No glyph carries meaning.** The small icon is decorative; every fact is in the text. This is the same rule 06-UI-SPEC states for in-app icons, and it survives here for free because the app cannot style the notification.
- **The tap target is the OS's.** The app defines no notification action buttons in v1.1 (which is also why the background isolate callback is not needed — 07-RESEARCH §5.3), so there is nothing for this phase to make activatable.
- **The one in-app assistive-tech surface is unchanged:** `BqNavBar`'s three destinations keep their own `onTap`-on-`Semantics` contract (06-UI-SPEC S8). Lifting the tab index out of `State` must not remove it. A test asserting activation via `SemanticsAction.tap` already exists and must stay green **unmodified**.
- **No text scaling concern exists** — but see the § Typography length budgets, which are the OS-surface equivalent: the OS truncates where the app would have wrapped.

Android renders the status-bar icon as a **monochrome silhouette**, so a full-colour launcher icon becomes a white blob. | `DarwinNotificationDetails.badgeNumber` | **not set** (`null` ⇒ the badge is not modified) | The app has no unread concept. A badge that only clears when the user opens the app is a persistent nagging surface, which spec §2.5 rules out. Consistent with `requestBadgePermission: false` |
| Android `groupKey` / iOS `threadIdentifier` | **neither set** | Both platforms already bundle same-app notifications automatically. An explicit Android group wants a summary notification, which means a second, differently-worded message and another id against nothing; iOS groups by app by default. Recorded so an executor does not add either speculatively |

### DECIDED-19 — `visibility: NotificationVisibility.private`, and what it does not do

Set on **every** `AndroidNotificationDetails` — per-notification, because `AndroidNotificationChannel` has no `visibility` parameter at all (07-RESEARCH correction C-1). A task that says "set it once on the channel" produces public lock-screen content.

**Honest statement of its limits, so nobody mistakes it for the privacy control:** `VISIBILITY_PRIVATE` asks Android to conceal content on a secure lock screen — but whether it *does* depends on the user's own "sensitive notifications" setting. With Android's default ("show all content"), a private notification is shown in full. **The count-only text remains the actual privacy control on both platforms**, and on iOS it is the only one (no `hiddenPreviewsBodyPlaceholder` through this plugin). `visibility: private` honours a user who has asked for redaction; it does not create redaction.

### DECIDED-20 — iOS foreground presentation stays at defaults

The five `defaultPresent*` flags on `DarwinInitializationSettings` (`Alert`, `Sound`, `Badge`, `Banner`, `List`) keep their `true` defaults: a reminder that fires while the app is open still appears. Suppressing it would mean a dose reminder that silently never appears in one specific app state, and the notification is also the *record* in Notification Center. Mildly redundant when the user is already looking at Сьогодні; correct in every other case.

**Not to be confused with** the three `request*Permission` flags — `requestAlertPermission`, `requestSoundPermission`, `requestBadgePermission` — which **must all be `false`** (07-RESEARCH Pitfall 1). Leaving any of them `true` fires the one-and-only iOS prompt at `initialize()`, i.e. at launch, which sets NOTIF-03 on fire silently and unrecoverably. These two groups of flags sit in the same constructor and mean opposite things; the source gate in § Sign-Off Conditions exists because of that adjacency.

## 11. Interaction Contracts

1. **A notification fires** → the OS displays title + body. The app is not running code and cannot change what is shown. The text was frozen at scheduling time (§ 7.3).
2. **Tapping a notification, app warm** → tab index := 1 (Сьогодні) **and** `followToday()`. Nothing else changes (DECIDED-10).
3. **Tapping a notification while a route is pushed** → the tab changes under the route; nothing is popped (DECIDED-11).
4. **Tapping a notification, app cold** → launch details resolve before `runApp`; frame 1 renders Сьогодні, following today. No Стек frame is ever painted (DECIDED-12).
5. **Tapping with an unrecognized payload** → nothing happens. No navigation, no reset, no error surface (DECIDED-13).
6. **Dismissing a notification without tapping** → nothing happens. `NotificationResponseType.notificationDismissed` is not acted on; a dismissal is not a "taken" mark and must never become one.
7. **Saving the first regimen** → the write completes, the editor pops, then the OS permission dialog appears. Once per install (DECIDED-7, DECIDED-8).
8. **Granting permission** → reminders begin appearing at their times. **Nothing in the app changes visibly**, including on the screen the dialog was covering.
9. **Denying permission** → **nothing changes at all.** The app is fully functional; every screen is byte-identical to the granted case (DECIDED-9).
10. **Changing the app language** → every scheduled notification is re-issued in the new language, and the Android channel's name and description are updated in place (DECIDED-14, DECIDED-16). Already-delivered notifications are left as they are (DECIDED-17).
11. **Switching tabs, browsing a past day, opening any sheet** → unchanged from Phase 6 in every respect. Lifting the tab index out of `State` must not alter tab behaviour, `IndexedStack` mounting, `TickerMode` gating, or the browsed-day survival that `calendar_providers.dart:30-35` documents.
12. **Nothing in this phase writes domain data.** No `IntakeLog`, no `Regimen`, no `Supplement` is created, edited or deleted by any notification path. Marking a dose taken remains a deliberate in-app action, and Q-3 ("cancel the reminder for a dose already marked taken") stays deferred — which means a reminder can arrive for a dose the user already took. ## 13. Layout & i18n Rules

- **Every user-visible string from ARB, both files in the same commit.** Four keys added, none deleted, none rewritten.
- **Ukrainian carries all four CLDR plural forms** in `doseReminderBody`, following `substancesCount`. The 11-14 exception is exercised by a pinned fixture, not assumed.
- **No sentence is composed from concatenated localized fragments.** Title and body are each one whole ARB value; word order and the ` · ` separator are the translator's to move.
- **No fixed-width or fixed-height text container exists**, trivially — this phase lays out no text. The OS-surface analogue is the length budget (§ Typography), and it is checked the same way a `stripHeightFor` unit test is: by calling a pure function, not by pumping a widget.
- **`EdgeInsetsDirectional`-only** and the token-only rule (D-07) are reaffirmed and untouched: no file this phase adds imports `lib/core/theme/`.
- **The notification locale is observed, never re-derived** (DECIDED-15) — one resolution point, for the same reason the codebase keeps one activity decision point.
- **Time formatting outside a `BuildContext` happens in exactly one helper**, using `DateFormat.Hm(localeName)`, which is the non-context equivalent of the app-wide `alwaysUse24HourFormat: true` rule. No second time formatter may appear.
- **The tab-index lift must not weaken any existing accessibility contract.** `BqNavBar`'s per-destination `onTap`-on-`Semantics` (06-UI-SPEC S8, the WR-02 lesson) survives verbatim; the existing `SemanticsAction.tap` assertions must stay green **without being edited**. 07-RESEARCH §8.6 names the four test files the lift churns — that is rework to budget, not licence to relax an assertion.
- **The payload is untrusted local input** and is whitelisted by equality, the same stance `locale_controller.dart` takes for the stored locale tag.
