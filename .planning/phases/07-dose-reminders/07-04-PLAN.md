<objective>
Wire the reminders to reality: build the localized text, and re-derive the scheduled set whenever the things it depends on change.

Everything up to here has been correct in isolation. This plan connects it — the pure plan to the platform through the reconciler, and the reconciler to the events that change what the plan should say. Six triggers, one of which the approved spec's own list omits: a language change. A scheduled notification carries text frozen at scheduling time, so without that trigger a user who switches to English keeps Ukrainian banners for up to the whole horizon, silently, with nothing but a test able to notice.

The copy is where this phase's user-visible surface actually lives, and all of it is rendered by the operating system. That makes the length budgets and the plural forms the risk, and both are testable without a device.

Purpose: NOTIF-04 (re-derivation on every trigger, across midnight and a language change), NOTIF-01's copy (one notification naming how many doses are due), NOTIF-03's silent half (denied means nothing is scheduled).
Output: the localized text with its plural forms and length budgets pinned, and one debounced sync whose every platform call comes from a reconciled difference.
</objective>

A count rather than nothing at all, so a test can observe progress by listening and polling instead of by sleeping — an unlistened provider is paused in this version of Riverpod, so a test that merely builds a container observes nothing.

Its build reads the bootstrap flag first and returns immediately while it is false. Those three cover every trigger but one: a regimen created, edited, paused, resumed or deleted all reach the regimens stream because the cascade soft-deletes the regimen too; the day rolling over reaches the clock; and a language change reaches the resolved locale. The resume trigger is task 3.

Debounce before applying. The editor writes a regimen and its slots in one transaction but the stream can emit more than once, and each application is dozens of platform round trips — so a save that fires three applications is three times the work and three times the window in which the scheduled set is half-updated. Use a timer, cancel it on dispose, and make the delay a named constant with the reason beside it.

The application itself, in order: build the plan from the watched regimens, the current day and the current minute of day; render each entry's title and body through the copy layer in the resolved locale; ask the platform what is currently pending; reconcile; then issue the cancellations followed by the schedules.

**Name the clock, and use the app's existing one.** The day comes from the calendar clock provider, which is already the app's single sanctioned "what day is it" read. The **minute** must come from the same place — the injectable wall-clock function that controller holds, whose own doc calls it "the ONE wall-clock read in the app" — and never from a bare `DateTime.now()`. Two reasons, both concrete. First, that doc comment becomes false the moment a second wall-clock read appears, and this codebase treats its own doc comments as load-bearing. Second, the test harness's fake clock controls timers but never `DateTime.now()`, which is exactly why that seam was injected in the first place: with a bare read, plan 07-01's tested boundary — today's slots at or before now are dropped — becomes unpinnable from the sync's own tests, and the "a slot exactly at now" case goes back to being a race. Derive the minute of day from that one function and say so in a comment naming both reasons. Deliberately do **not** reach for the calendar tab's minute-ticker provider: it lives in a feature `core` may not import, it is `autoDispose`, and it re-emits every sixty seconds — watching it would turn the sync into a once-a-minute rescheduler. Cancel before schedule so a re-issued id is never momentarily registered twice — the reconciler deliberately encodes no ordering because this is the caller's decision, and this is the caller making it.

Choose the scheduling shape from the planned entry's own tier. A repeat and a one-shot are separate methods on the seam precisely so that "a course must never repeat" is structurally true rather than dependent on a conditional argument.

Gate the whole application on the seam's enabled check.
