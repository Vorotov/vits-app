Create the three pure files, tests first for every behaviour above.

**`notification_constants.dart`** holds the values more than one layer needs and nothing else: the Android channel id, the tap payload token, the index of the Сьогодні destination, a predicate answering whether a payload string is the known token, and the two scheduling numbers (the pending-request budget of 60 and the 30-day horizon, whichever binds first — spec §2.3). Both numbers carry a doc comment saying what they protect: the budget exists so the app never discovers what iOS does at its own 64-request ceiling, and it is enforced in the pure plan rather than in the service precisely so that no platform behaviour is ever load-bearing (risk R-11). The channel id is deliberately not re-versioned to change its language — see the ARB task; a doc comment records that so nobody "fixes" it.

The payload predicate is an **equality check against one constant**, and the doc comment must say why it is a whitelist rather than a parse: the operating system persists the payload across app updates and can replay it, so it is untrusted local input in exactly the sense the stored locale tag already is (`locale_controller.dart` takes the same stance for the same reason). Anything else — an older build's payload, a null, an unknown string — answers false and produces no navigation at all.

**`tz_conversion.dart`** is the adapter that keeps `package:timezone` out of the domain. Three top-level members:

`initTimeZones({Future<String> Function()? readDeviceZone})` loads the FULL zone database and then resolves the device zone. It must load the complete database, not the trimmed one: research ran both, and the trimmed database throws a location-not-found error for the deprecated Ukrainian alias that some Android builds still report — i.e. it fails on precisely this app's primary audience. The device-zone read is injectable for the same reason `TodayController`'s wall-clock read is (`today_controller.dart:47`): it is a platform-channel round trip, so without the seam none of this file is testable at all, and every test in this repo would have to reach a plugin. Production defaults to the plugin-free package's own reader. Failure to resolve the zone is caught, reported through the crash-report facility in the shape `main.dart:28-36` establishes, and degraded — a wrong zone costs correct reminder times, a thrown error costs the whole app, and this file must never be able to hold the launch hostage.

**Do not name a fallback zone with a bare string literal.** The degrade path must fall back to the package's own default location constant, not to a hand-written zone name: that name would be a fourth flagged literal in the classification gate below, and adding it to the allowlist entry would be paying an exemption for something the package already exposes as a value. If the package genuinely offers no such constant, add it to the same allowlist entry **in this commit** with its own rationale rather than leaving the gate red.

`instantFor({required DateTime day, required int minutesFromMidnight})` is the one line the whole phase's correctness turns on. Build the zoned value **field-wise** from the day's own year, month and day components plus the hour and minute derived from the minute-of-day. Never convert the date-only value to local time first: a date-only value is a UTC-normalized calendar day by the project's own rule (`cycle_math.dart:11-16`), and converting it would shift the whole day backwards for every zone west of the meridian — a Ukrainian user would never see it and an American user would get every reminder on the wrong date. This is the exact inverse of `dateOnly()` and it deserves the same doc-comment treatment: say what it is the inverse of, say what the wrong shape looks like, and say what it costs.

`nextDailyOccurrence({required int minutesFromMidnight, required zoned now})` answers where a repeating request's first fire lands. It exists in this plan even though nothing calls it until plan 07-02, because it is the tier-A half of the same boundary and splitting one boundary across two waves is how the two halves drift.

Guard the ordering with a library-private initialized flag set by `initTimeZones` and asserted by both constructors. Building a zoned value before the local location is set yields UTC **silently** — every reminder off by the device's offset, two or three hours for this app's audience, with nothing at runtime to show it. An assertion is the only thing that turns a silent wrong answer into a loud one.

**`notification_plan.dart`** is the whole correctness surface and imports the two pure domain libraries and the constants file only — no timezone, no plugin, no Flutter, no clock. Declare `PlannedNotification` carrying an id, a nullable day (null meaning a daily repeat), the minute of day, and the dose count. Derive the "repeats daily" answer from the nullable day rather than storing it as a second field, so the two can never disagree; research's suggested shape carried both and that is one invariant more than the type needs. Do not carry the payload on it either — there is exactly one payload token in the whole app, so a per-notification field would be a place for a second one to appear.
