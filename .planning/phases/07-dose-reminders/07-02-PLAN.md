<objective>
Complete the correctness surface: promote the times that can be a single repeating request, and compute the difference between what should be scheduled and what already is.

Plan 07-01 proved the pipeline with every notification as an individually scheduled one-shot. That is correct but expensive on iOS, where the pending-request ceiling is a hard platform limit and a *repeating* request costs one slot regardless of how many times it fires. This plan adds the promotion — roughly tripling the effective horizon for a daily stack — and the reconciler that makes every re-derivation a difference rather than a rebuild.

Both halves are pure and both are where this phase's correctness actually lives (spec §2.4). Nothing here imports a clock, a timezone, a plugin or a Flutter library.

Purpose: NOTIF-01 (grouping and the tier split), NOTIF-02 (staying inside the pending-request budget by spending one request where a repeat will do), NOTIF-04 (re-derivation as a diff).
Output: a tier-aware plan whose repeats are structurally protected from truncation, and a `reconcile` that detects stale copy as well as a stale set.
</objective>

- `runsEveryDayFrom(Regimen, DateTime today)` in `lib/core/domain/cycle_math.dart`, plus a property test binding it to `isActiveOn`.
- Tier promotion inside `planNotifications`, with the repeats-first ordering that protects them from budget truncation.
- `reconcile(...)` and its `DesiredNotification` / `ScheduledNotification` value types in `notification_plan.dart`.

Add `runsEveryDayFrom(Regimen r, DateTime today)` to `cycle_math.dart`, directly below `isActiveOn`.

It answers exactly one question: will this regimen be active on **every** day from today onward, forever? True only for a cyclic regimen that is not paused, has a positive on-day count, has a zero off-day count, and whose start date is not after today. A cyclic regimen ignores its end date, so the end date plays no part; a course always answers false because it has a last day.

The future-start condition is the one research had to correct into its own statement, and the comment must say why it is there rather than looking like belt-and-braces: a daily regimen starting next week satisfies every other condition today, and promoting it would arm a repeating request that starts firing before the regimen begins. It becomes promotable on its start date, at which point the ordinary re-derivation picks it up — which is why nothing else is needed to handle it.

**This function lives in this file and not in `lib/core/notifications/` for one reason, and the doc comment must state it:** it mirrors two of the guard conditions inside `isActiveOn`'s cyclic arm, so it is coupled to that function's internals in a way no amount of care at a distance can protect. Keeping it one screenful below the thing it mirrors means a future change to the activity rule — a new regimen kind, a new pre-start rule, a new pause semantic — is made by someone who is looking straight at the predicate that depends on it. The same reasoning `planner_view_model.dart` records for having exactly one activity decision point applies to having exactly one *place* where that decision's shape is mirrored.

Then write the property test, which is the real deliverable of this task. A comment claiming the predicate agrees with `isActiveOn` is worth nothing; a test that generates regimens across the parameter space, and for each one the predicate accepts asserts `isActiveOn` holds on every day of a 400-day walk, is worth a great deal — it is what will fail the day the two drift. Choose a fixed generation seed and say so, so a failure is reproducible.

400 days rather than a month: it must cross a year boundary and both DST transitions, which is the same reason the existing cycle-math tests reach that far.

**The negative direction needs a bounded generator, and the bound is part of the property rather than a convenience.** Include it — without it a predicate that answered false to everything would pass the positive direction trivially — but state it correctly, because the naive form is FALSE. Two shapes make the predicate answer false while `isActiveOn` holds across all 400 days:

1. a **course** that starts on or before today and whose inclusive end date is on or after `today + 399` — the predicate correctly answers false because a course ends, yet it has not ended inside the walk;
2. a **cyclic** regimen with a non-zero off-day count and an on-day count of 400 or more — the predicate correctly answers false because it has breaks, yet the first break falls outside the walk.

Neither is a defect in the predicate; both are the walk being too short to observe the lapse. So bound the generated set so that every regimen it produces lapses within the walk: cyclic on-days in 1..30 and off-days in 0..14, and course end dates within `today + 120`. Those ranges also match what this product's own editor can produce, which is why the bound costs nothing in coverage.

Name both excluded shapes in a comment above the test, with the reason, so a future reader widening the generator learns why the bound exists before the test goes red on them. And do **not** list the future-start daily regimen as an exemption: its `isActiveOn` is false on day zero of the walk, so the negative direction holds for it. What is special about it is only that its predicate answer changes when its start date arrives — worth one sentence in the same comment, not an exception.

  <action>
Add `reconcile` to `notification_plan.dart`, beside the plan it reconciles, along with the small value type pairing a planned entry with its already-rendered title and body.

It takes the desired set — planned entries each carrying the text that WILL be scheduled — and the pending set as the platform reports it, and returns the ids to cancel and the entries to schedule. Four rules: matched id with matching text is satisfied and appears in neither output; matched id with differing text is cancelled and re-scheduled; a pending id not desired is cancelled; a desired id not pending is scheduled.

The third rule is what makes a language change work, and the comment must explain the trap rather than just implementing past it. Ids are derived from tier, time and date; **they carry no locale**. A language change therefore produces an identical desired id set, so an id-only set difference computes an empty diff and does nothing at all — the notifications keep their old-language text for up to the whole horizon, silently, with nothing but a test able to notice. Comparing the text as well is self-correcting in a second way that is worth having on its own: it also repairs a re-derivation that was interrupted halfway through, with no special-case trigger and no persisted "we were in the middle of something" flag. The alternative the UI contract also permits — treating a language change as a distinguished trigger that forces a full cancel-and-reschedule — was not chosen, and the reason belongs in the comment: it needs the trigger to be plumbed correctly forever, whereas comparing what is actually there needs nothing to be remembered.

Comparing the text is possible only because the platform's pending-request record happens to carry the title and body. Say so, and say that it carries no scheduled time — which is the same fact, seen from the other side, that forces the fire time into the id.

**Never return an instruction to clear everything.** A blanket clear also dismisses reminders that were delivered and that the user has not acted on yet, and it leaves a window in which nothing at all is scheduled. Cancelling by id is not merely tidier; it is the difference between a re-derivation the user cannot perceive and one that eats a notification they were about to act on. The phase carries a source gate asserting the blanket call appears nowhere in the app, and this function is the reason it can.

Note in the doc comment that the function is pure and deliberately does no I/O ordering: cancels before schedules, or interleaved, is the caller's concern, and the caller has a reason to prefer one. Do not encode an ordering here that the caller then has to work around.
  </action>
