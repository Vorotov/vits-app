<objective>
Ask for permission at the one moment it means something, at most once per install — and tell the user, in Settings, whether reminders are allowed, with a way back if they are not.

These two belong in one plan because they are two halves of one problem. The bare operating-system dialog was chosen deliberately over a priming sheet, and that choice has a real cost: a reflexive refusal on iOS cannot be re-requested from inside the app, ever. The project owner resolved that by adding recovery rather than persuasion — a state row and a control that opens the operating system's own settings — which is the cheaper and more honest half. Neither half is safe to build without the other, because the ask is what creates the state the row reports.

The Settings screen is the most heavily gated surface in this codebase: its source gates forbid a numeral, a loading surface, an error surface, a formatter, a database reference, a locale-keyed branch, a hex colour and any font size outside a closed list. **Every one of those gates must pass unmodified.** They are enumerated in task 3 because they are the actual difficulty of this plan.

Purpose: NOTIF-03 (asked at first save, silent when denied), NOTIF-05 (Settings states whether reminders are allowed and offers a way to the operating system's settings).
Output: the permission controller, the ask at the save call site, and one row on an otherwise untouched Settings screen.
</objective>

Create `notification_permission.dart` with an app-lifetime notifier over a nullable boolean: unknown, allowed, not allowed. Three states rather than two, and the unknown one is load-bearing — the platform answer is a future, neither platform can tell "denied" from "never asked", and a screen that must not lie needs a way to say nothing yet. The default no-op seam answers unknown, which is what keeps every existing widget test's tree identical.

Its build returns unknown and kicks off a refresh; it also installs an app-lifecycle listener that refreshes on resume, disposed with the controller, following the calendar clock's precedent. The resume refresh is what makes the Settings row self-correcting: returning from the operating system's own settings screen **is** a resume, so a user who just switched reminders back on sees the row change with no further action and no manual retry control — which is fortunate, because the Settings screen's own gates forbid a retry affordance.

The ask does three things in order: check the persisted flag and return immediately if it is set; issue the request; record the flag and refresh. Gate it on a persisted boolean and say why in the doc comment, because a reader will otherwise see a redundant guard in front of an idempotent-looking platform call: without it, Android re-shows its rationale dialog on **every** regimen save until the user has denied twice, which is exactly the nagging the approved spec rules out, and neither platform's API can answer "have we ever asked?" for us. Store it beside the language override, in the same key-value store, following the same precedent for small non-domain state — never in the database, which this state has no business in.

Read the stored value the way the language override is read: as an untrusted object with its type checked, not through a typed getter that performs an unguarded downcast. The type of untrusted storage is as untrusted as its content. A null store means the store could not be opened at all, which is the same state an empty store leaves — ask, and accept that the memory is lost.

Every failure on this path is absorbed and reported to the crash logger, never surfaced: the request may throw, the write may be rejected, the settings call may fail off-platform. Use the crash-report shape the bootstrap already establishes for the two failures this app deliberately swallows. **Nothing on this path may produce a user-visible surface** — that is the same requirement as the no-primer decision, seen from the failure side.
