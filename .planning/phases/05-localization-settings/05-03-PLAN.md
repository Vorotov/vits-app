  <action>
Write the gate that decides whether criterion 4 survives contact with the next contributor. Read the ARB directory off disk as the source of truth and assert every other representation agrees with it. Six assertions, all in one file:

1. Glob proof, first and unconditionally: the ARB directory listing resolves at least two files matching the `app_&lt;code&gt;.arb` shape, with a `reason:` naming the consequence — a gate over an empty file set passes silently and protects nothing.
2. `AppLocalizations.supportedLocales` language codes, sorted, equal the ARB codes on disk, sorted. The generated list is the filesystem, not a hand-kept list.
3. `LocaleController.supportedLanguageCodes` equals the ARB code set on disk. The controller derives; it does not enumerate.
4. The fallback is DECLARED, in two parts, and both parts are required:
   (a) `AppLocalizations.supportedLocales.first` is the English locale, with a `reason:` explaining that `MaterialApp` falls back to `supportedLocales.first`;
   (b) `l10n.yaml`, read off disk as text and stripped of comment lines, declares a `preferred-supported-locales` key whose first list entry is the English language code.
   Part (b) is the load-bearing half: English currently sorts first alphabetically, so part (a) alone passes even with the declaration deleted. State that in the `reason:` so nobody later removes (b) as redundant.
5. Every ARB code resolves through `lookupAppLocalizations` to a non-empty `languageName`, and the names are pairwise distinct. Use the SYNCHRONOUS lookup here, not the async delegate load — the picker uses the synchronous one and this assertion exists to prove that path cannot throw for any shipped locale.
6. Every ARB code is a member of `kMaterialSupportedLanguages`, with a `reason:` naming the consequence — outside that 82-language set `GlobalMaterialLocalizations.load` asserts in debug and Material chrome is untranslated, so such a language would need a custom delegate, i.e. a code change, which criterion 4 forbids.

Plus the untranslated-messages assertion (PF-2): the `l10n-untranslated.json` artifact declared in `l10n.yaml` is either absent or parses to an empty JSON object. A key missing from a non-template ARB does not fail the gen-l10n build — it silently falls back to the template's English message — and this is the only mechanical thing standing between that behaviour and a Ukrainian screen with one English sentence in the middle of it.

Synthetic third locale — this is what makes the file a proof of criterion 4 rather than a restatement of the current two languages. Add a group that constructs a locale code that is NOT on disk and asserts the negative half of the contract: it is absent from `AppLocalizations.supportedLocales`, absent from the controller's derived set, and a stored preference holding it sanitizes to null rather than reaching the generated lookup. Then assert the positive half structurally: for EVERY code the ARB directory yields — written as a loop over the discovered set, never over a literal pair — assertions 5 and 6 hold. Written that way, dropping `app_pl.arb` into the directory extends this test's coverage with no edit to it, which is the same property criterion 4 claims for the app.

Do NOT write an ARB into a temp directory and shell out to `flutter gen-l10n`. No test in this repository spawns a process, the assertions above catch every code-shaped violation, and inventing a subprocess-test convention in the final v1 phase is a cost with no matching benefit (05-PATTERNS § No Analog Found; RESEARCH A9 marks the shell-out strictly optional).

Test names state the behavioural claim and cite the ID, in house style.
  </action>
