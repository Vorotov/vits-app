    Behaviour that must be true after this task, and that Task 2 encodes as tests:
    - A provider that has failed and is inside Riverpod's retry backoff renders the screen's designed error copy plus its retry control, on the first frame after the failure.
    - A provider that is loading with NO error still renders the designed loading treatment (empty area on Stack and Planner, the held previous-day list on Calendar) — the fix must not turn a genuine first load into an error surface.
    - A provider that recovers renders its data surface again; the existing retry-then-recover tests keep passing unchanged.
    - No raw exception or stack-trace text reaches the tree in any of these states.
  </behavior>

  <action>
Three surfaces, one rule: an `AsyncValue` that carries an error renders the error surface regardless of whether it is also loading.

Site 1 — `planner_screen.dart` `_surface`: change the first switch arm from the `AsyncError()` pattern to the property pattern that matches any `AsyncValue` whose `hasError` is true, keeping the remaining three arms and their order exactly as they are. Replace the arm's inline comment with the explanation given verbatim in RESEARCH § Code Examples: Riverpod 3 reports a failing provider as an `AsyncLoading` that CARRIES the error while it retries on its own backoff, so matching the error subtype alone leaves the arm unreached for the whole backoff window and the screen renders the blank loading surface instead of the designed one. Cite 04-REVIEW.md CR-02. Also update the `_surface` doc comment above it (lines 595-600), which currently states the arm order as designed behaviour and would otherwise document the defect.

Site 2 — `stack_screen.dart`: add `skipLoadingOnReload: true` as the FIRST named argument of the `entries.when(...)` call. Leave the `data:`, `loading:` and `error:` arms and their comments untouched — the loading arm's "no spinner, the stream resolves within a frame" rationale is still correct for a genuine first load.

Site 3 — `calendar_screen.dart`: the same single named argument on the `widget.doses.when(...)` call. The held-list loading arm and its `IgnorePointer`/WR-01 rationale stay exactly as they are; what changes is only that a held list no longer wins over an error.

Add nothing else. Do NOT disable auto-retry in application code: it genuinely self-heals a transient failure, and `ProviderScope(retry:)` is a blunt global that would remove self-healing everywhere to fix a rendering rule at three call sites. The retry override belongs in tests only, and only where recovery rather than the retry window is under test — the existing precedent is already in the planner test file.
  </action>
