<objective>
Give the weekly load chart a y-axis that is not a limit: bars scale against the number of supplements currently carrying a schedule, so a full bar means "every scheduled supplement in your stack overlaps this week."

Removing the editorial limit removes the chart's old denominator — v1 sized bars against it, so the limit *was* the scale. This plan installs the replacement and neutralizes the chart's colour, reference line and over-bar. The verdict chips, the limit constants themselves and the copy purge follow in plan 06-06, which is why this plan does **not** delete the limit constant: the week-detail card, the year grid and the summary chips still reference it until then, and a green suite at every commit is worth more than deleting it one plan earlier.

Purpose: PLAN-05, the chart half.
Output: a self-scaling chart with one bar colour, a factual scale caption, and zero threshold geometry.
</objective>

## Artifacts this plan produces

- A scheduled-supplement ceiling on `CyclesModel`, computed in `planner_view_model.dart` next to the week loads, with a doc comment recording the `load <= ceiling` invariant and why it makes an over-bar unnecessary.
- ARB key `loadScaleCaption` — uk «повний стовпчик — увесь стек» · en "full bar = your whole stack" — in both locales.
- Chart tests covering zero / one / many and the no-chart path.

## Artifacts this plan removes

- The chart's threshold geometry: the offset, dash-on, dash-off and width constants, the `PositionedDirectional` carrying the `load-threshold` key, and the dashed-line custom painter (`planner_load_chart.dart:73-77, 177-184, 371-391`).
- The over-bar: the second height computation and the `load-over-$index` container (`:269-272, :321-332`).
- The three-way bar-colour ternary at `:273-277` — every bar is now the single neutral bar token.
- The old axis-centre legend call (`:199-202`), replaced in the same slot by the new caption.
- The `weekLoadLabel(load, slotsCount(editorialLimit))` wrapper inside the week-column `weekBarSemantics` call (`:292`), replaced by a plain `substancesCount(load)`. The `weekBarSemantics` key stays; its argument stops naming a limit. This clears `weekLoadLabel`'s last consumer in `lib/`, which plan 06-06 depends on before it deletes the key.
- **Not** removed here, deliberately: the limit and comfort constants (still referenced by the week detail, year grid and chips until plan 06-06), the `load == 0` 2px stub (geometry, not limit framing — it survives unchanged), and the dashed-line colour token (deleted in 06-06 once its sole consumer is gone).

  <behavior>
    - For a stack where every supplement carries a schedule, the ceiling equals the number of supplements.
    - A supplement with no schedule does not raise the ceiling.
    - A paused or deleted supplement is counted or excluded exactly as the week loads count or exclude it — the two are derived from the same collection.
    - For every week bucket in a generated model, the bucket's load is less than or equal to the ceiling. This invariant holds for randomly generated stacks, not just hand-picked ones.
    - A stack where exactly one supplement carries a schedule yields a ceiling of 1, and a week in which it is active yields load == ceiling.
    - A stack where no supplement carries a schedule yields a ceiling of 0.
  </behavior>
  <action>
Add a ceiling field to `CyclesModel` holding the number of supplements that currently carry a schedule, and fill it in the model builder next to where the week loads are computed. Derive it from the **same collection the week loads are derived from** — not from a separately filtered list — so that `load <= ceiling` holds by construction rather than by coincidence. That invariant is the whole reason no cap, no clipping branch and no over-bar are needed downstream, so state it in the field's doc comment along with the reason.

This is a model concern, not a widget constant: a scale that lives in a widget is a magic number waiting to be mistaken for a rule. Nothing in `planner_load_chart.dart` may compute or default this value.

Do not delete the limit or comfort constants in this task — the week-detail card, the year grid and the two summary chips still reference them until plan 06-06, and deleting them here would leave the tree uncompilable.

Write the behaviour tests above first, including the invariant test over generated stacks. The zero case is the one most likely to be got wrong later, so test it explicitly rather than relying on the empty state to hide it.
