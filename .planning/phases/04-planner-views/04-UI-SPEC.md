# Phase 4 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.
>
> **Scope note:** Phase 4 delivers ONE new screen surface — the Планувальник, rendered as a second page *inside* the Calendar tab — carrying two segments: **Цикли** (mockup screen 03 · ЦИКЛИ, lines 276-388) and **Рік** (mockup screen 04 · РІК, lines 390-468). It also amends the Phase-3 Calendar/Today screen with one entry affordance (DECIDED-1). Authoritative visual source: `claude_design_mockup/Boostque v0.1.dc.html`; every line citation below refers to it. The mockup is authoritative for *visuals*, not *scope* — see "Mockup Deviations Locked for v1".
>
> **Consumption rule:** the design system is ESTABLISHED (Phases 1-3). All styling goes through `BqColors` / `BqSeriesColors` / `BqRadii` / `BqSpace` / `BqText.mono()` / `bqTheme()` in `lib/core/theme/` and the existing `BqSegmented` widget — tokens are referenced BY NAME. Genuinely new mockup-sourced values appear ONLY in the "Token Additions" table (8 colors, 0 radii); nothing else may introduce a literal (D-07).
>
> **Read-only mandate:** these screens are pure projections of `isActiveOn`. They write nothing, materialize no `IntakeLog` row, and never import `dayDosesProvider` / `ensureLogsForDay` (Phase-3 WR-06 lesson). This is a *design* contract clause as much as an architectural one: no control on either segment may look like it changes data.
>
> **Discretion resolved:** 04-RESEARCH.md flagged 12 ASSUMED items (A1-A12) and 4 Open Questions. All are DECIDED here (sections marked **DECIDED**) — the executor implements them as written; UAT may revisit, but the planner must not treat any of them as open.

## Discretion Resolved

**DECIDED-1 — How the user reaches the planner (Open Question 1, A1).**
The planner is a **second page inside the Calendar tab**, entered from a `plannerTitle` text button in the Today header's action `Wrap` and left by a `‹ Сьогодні` control in the planner header (plus system back).
*Mockup evidence:* both planner screens keep **Календар** selected in the nav bar (`background:#4A4E7C` on the Календар destination, outlined on the others — lines 382, 462), so the planner lives under Calendar, not in a fourth tab (which would also break the Phase-1 three-tab success criterion, ROADMAP:31). The section caption over the whole group reads `день · цикли · рік · розклад` (line 189) — four *peer* screens. Screen 02 carries no segmented control (lines 203-223), so the planner is a distinct screen and the Рік/Цикли control switches *within* it, not within Today.
*Why a page swap, not a push:* `AppShell` is an `IndexedStack` that keeps every child mounted (`lib/app_shell.dart:38-45`); a root-level `Navigator.push` would cover the `NavigationBar` the mockup deliberately shows on both planner screens.
*Why a text button in the header, not an icon or a persistent band:* an icon would be the first icon-font glyph on a screen the Phase-3 contract deliberately kept glyph-free, and it would need a tooltip to be honest; a persistent entry band below the week strip would push the dose list — the core loop — down by ~44px on the app's most-used screen. A text action inside the already-`Expanded` title column costs no layout risk and reuses the exact `backToToday` pattern the user has already met.
*Reversal path:* the planner screen is navigation-agnostic; switching to a nested `Navigator` later touches only `CalendarScreen`.

**DECIDED-2 — The dashed reference line stays at comfort-3, and there is only one (Open Question 2, A7).**
*Evidence:* the mockup's line is at `bottom:22.8px` = 0.6 × 38px, i.e. exactly load 3 (line 339), and the axis caption names both numbers — `межа 5 · комфорт 3` (line 348).
*Rationale:* the 5-line needs no ink because it is already **structural** — the main bar is capped at 38px = load 5, and everything above it is the `risk` over-bar, so the limit is drawn as a *colour change at exactly the right height*. A second dashed line there would land on that same boundary and read as redundant chrome on a 46px chart. PLAN-02's "against the editorial 5-substance line" is satisfied five times over: the structural cap, the `limitBadge` "межа 5", the five slot pips, the verdict chip, and the axis caption. Neither line is ever labelled as a safety threshold; the axis caption's two words ("межа", "комфорт") are the only labels either gets.

**DECIDED-3 — Week buckets are full Monday weeks; a zero-load week still draws (A3, P-6).**
Buckets run Monday→Sunday, from `mondayOfWeek(windowStart)` through the week containing `windowEnd − 1` — **18 or 19 buckets**, every one exactly 7 days. This deviates from the mockup's window-aligned `i * 7` arithmetic (line 765) for two reasons: DECIDED-4 of Phase 3 locked Monday-first weeks in every locale, and the summary chip literally says "Цього тижня" (line 920), which must mean the *calendar* week containing today, not a bucket that happens to straddle it. Clamping the first bucket instead was rejected — a month starting on a Sunday would produce a 1-day bucket whose bar is honestly low but visually a lie next to seventeen 7-day bars. Consequence, accepted: the first bucket may begin up to 6 days before the 1st and the last may end up to 6 days after the window, so the axis labels show the **actual** bucket start/end dates rather than the mockup's "1 серп / 30 лис" (M6).
`mondayOfWeek` is promoted from `week_strip.dart` into `core/domain/cycle_math.dart` and the strip imports it there (A4) — a feature file must not import another feature's widget file.
A `load == 0` week renders a 2px `field` stub rather than nothing (mockup `h` would be `0px`, line 905): a column with no pixels reads as a gap in the chart and gives the tap target no visible anchor.

**DECIDED-4 — A run is planned as a whole, or not at all (A6, P-5).**
Verbatim mockup rule, minus the `risk` branch: `s[0] > TODAY ? 'planned' : 'active'` (line 639). A run whose first day is after today is entirely hatched; a run already in progress stays solid to its end, including its future tail. Splitting a running cycle at today was rejected because `statusOf` already returns `planned` exactly when "today is before startDate" (`stack_status.dart:37`) — keeping the mockup rule means a supplement's first hatched segment and its ЗАПЛАНОВАНО stack chip always agree. One-line reversal in `ganttSegments` if UAT disagrees.

**DECIDED-5 — No cap on the year grid (Open Question 3, E-16).**
Month cards grow with the stack (one 4px bar + 3px gap per supplement). At N = 20 a card is ~160px and the grid ~500px — tall, but honest and simple; a "+N more" affordance would hide exactly the overlap the screen exists to show. The computed `mainAxisExtent` makes this safe at any N and any text scale. Revisit only if UAT with a large stack looks bad.

**DECIDED-6 — The `>=` / `>` asymmetry ships verbatim (Open Question 4).**
The Цикли summary chip goes amber at `load >= 5` (line 918); the Рік peak chip goes amber at `load > 5` (line 969). Both are transcribed as written, and the asymmetry is *deliberate and defensible*: a week sitting exactly at the limit is worth a nudge because the user can still move a start date, while a month that merely touches the limit for a few days is not — the month view flags only genuine exceedance. **Recorded here so a later reader does not "fix" it.** Raise at UAT as a question, never as a bug.

**DECIDED-7 — Which rows exist, and what "empty" means (A5, PF-9, E-1/E-2).**
- Supplements **with no regimen** (`StackStatus.fresh`) are excluded from the gantt, the load chart and the year grid — there is no schedule to draw and no coverage to compute. They remain fully visible on the Stack tab.
- **Paused** regimens keep their gantt row with a bare `chip` track (the mockup's `пауза` legend swatch is the same `#F2F1EE` as the row track — lines 316, 329, which is the design's own way of saying "a paused row is an empty track"), contribute 0 to every week load and every month cell, and are filtered out of month-detail rows by `frac > 0`. Consistent with REGI-04.
- The **empty state** therefore fires when the stack is empty *or* when every entry is fresh, with the two body variants in the Copywriting Contract distinguishing the two — a user who owns supplements should never be told to go add one.
- A course with a null `endDate` contributes no runs anywhere (PF-11) — correct and identical to the Today screen; no special-casing.

**DECIDED-8 — Copy safety: the truncated note, and one disclaimer on both segments (A8, PF-5, PF-12 — PLAN-04).**
- `weekNoteOverLimit` ships **truncated** after "…обговорити такий обсяг із лікарем." The mockup's trailing clause "— зокрема через сумарне навантаження жиророзчинними формами" (line 785) is a pharmacological claim that sits squarely inside the never-ship interaction-advice exclusion (REQUIREMENTS Out of Scope). "Talk to a doctor" is a referral, not advice, and is consistent with the disclaimer. If the truncation reads oddly in uk, rewrite the final sentence — **never restore the clause.**
- The Year screen's mockup footnote (line 454) contains **no** disclaimer, while the Cycles footnote (line 374) does. PLAN-04 requires *every* planner screen to carry it. Closure: **both segments render the same `plannerDisclaimer` key as their last element**, and Рік renders `yearFootnote` above it. Appending the bare `disclaimerEducational` to Рік was rejected — it would leave the Year screen without the *editorial framing of the 5-limit*, which is the half of PLAN-04 that actually does the work, and it would make the two segments assert the disclaimer with different strings (untestable by one finder). This is a deliberate, requirement-driven addition to the mockup, recorded as M9 — not a transcription error.

**DECIDED-9 — The Year matrix is always `today.year`, Jan–Dec, with no paging (A9).**
PLAN-03 says "12 month cards", not "any year". The Цикли window may cross into the next year while Рік stays on the current one — the two views intentionally show different spans (E-8), and the subtitle says which. Year paging is additive if it is ever wanted.

**DECIDED-10 — Touch targets on an 18-bar chart (A11, PF-8).**
Each week column is ~15px wide inside a 390pt screen — inherently below the 44pt guidance, and not fixable without changing the chart's information density. Mitigations, all required:
- The **whole column** is the hit target via `HitTestBehavior.opaque` spanning the full 46px chart height *plus* the 7px above the tallest bar → ≥53px tall.
- `Semantics(button: true, selected: …, label: weekBarSemantics, onTap: …)` sits on the **column node itself**, never on a descendant — `excludeSemantics` drops descendant actions (the WR-02 lesson from `week_strip.dart:262-268`). Assistive tech does not depend on physical target size, so AT parity is complete.
- Selection is **non-destructive, instantly visible, and self-correcting**: a mis-tap selects an adjacent week, the detail card updates, the chosen bar goes to full opacity, and a second tap fixes it. Nothing is written, so no mis-tap can cost the user anything — which is what makes the density acceptable here and would not make it acceptable on a write surface.
- Month cards in the year grid are ~78×N px and comfortably exceed 44pt; no mitigation needed there.

## Interaction Contracts

1. **Tap `plannerTitle` on the Calendar header** → the Calendar tab swaps to the planner page. **Tap `‹ Сьогодні`, or press system back** → back to the Today page. No route is pushed; the nav bar never moves.
2. **Tap a segment (Рік / Цикли)** → swaps the body instantly. Each segment keeps its own selection (selected week, selected month) for the lifetime of the screen — switching to Рік and back does not reset the chosen week.
3. **Tap a week column** → selects that week; the column goes to opacity 1.0, all others to 0.5, and the inline week-detail card re-renders. Never a modal sheet (the user is comparing the detail *against* the chart — P-13).
4. **Tap a month card** → selects that month; its fill/border change and the inline month-detail card re-renders. Never a modal sheet.
5. **No gesture on either segment writes anything.** There is no long-press, no swipe action, no drag. If a control looks tappable it selects; nothing else.
6. **The planner never materializes.** It reads `stackEntriesProvider` and `todayProvider` and nothing else from `core/providers.dart`; `dayDosesProvider` / `dayDosesReadOnlyProvider` / `ensureLogsForDay` / `IntakeRepository` are unreachable from `features/calendar/planner_*.dart` (grep gate + a row-count regression test).
7. **The derived model is never computed in `build()`** — one `Provider` per view watches `stackEntriesProvider` + `todayProvider`; the widgets only read it. Riverpod's cache is the memoization.
8. **Live updates:** editing, pausing, resuming or deleting a regimen on the Stack tab re-emits `stackEntriesProvider`, so the gantt, chart and grid recompute with no manual refresh (the `IndexedStack` keeps both tabs mounted).
9. **Midnight rollover:** `todayProvider` flips → the today marker moves, a run starting today flips from planned to active, and the week/month selection follows unless the user picked one explicitly.
10. **Tap targets:** month cards and the two text buttons are ≥44pt; week columns are governed by DECIDED-10. Every selectable node carries `Semantics(button: true, selected: …, onTap: …)` **on the node itself**.
11. **Pressed states:** default Material ink ripple inside the shape for month cards; the load chart's columns show no ripple (the opacity change is the feedback). No Material elevation anywhere on these screens.
12. **`RepaintBoundary`** wraps the gantt card so week selection never repaints it.

## Layout & i18n Rules

- `EdgeInsetsDirectional` only; no fixed-width container around any `Text` (locked; uk runs 15-25% longer than en). The gantt row label, the month-card header and the month-detail row are the three high-risk spots — all three use a flexible text child and a non-flexible trailing element, never three rigid children (WR-04).
- **No fixed vertical extent around text either.** The year grid's `mainAxisExtent` is computed as `fixed + scaler.scale(textPart)` in the `stripHeightFor` idiom (`week_strip.dart:60-78`); the gantt track (11px), the chart (46px) and the coverage bars (4px) are pure geometry with no text inside and may stay constant (CR-01).
- Every user-visible string from ARB keys, both files in the same commit; every count key carries all four uk CLDR plural forms and is exercised at 1/2/5/11/21. Counts are composed by pre-formatting the plural string and passing it into the sentence key (the `cycleSummaryCyclic` convention).
- **Month-name case is a correctness rule, not a style choice (PF-4):** every month name on these screens stands alone, so it uses the *standalone* pattern letters — `LLLL` for the full nominative form (Цикли subtitle "серпень — листопад", peak-month label, month-detail title) and `LLL` for the abbreviations (gantt month header, month-card label). `MMMM`/`MMM` (genitive: "серпня") is correct **only** where a day number is present — the week range and the chart's axis dates (`d MMM`). Pin both with a unit test asserting the exact uk output; never a hardcoded month table.
- Uppercased labels (gantt months, month-card labels, month-detail title) use locale-aware `toUpperCase()` on the `intl` output, never a hardcoded uppercase string.
- All numerals via `BqText.mono()` with tabular figures, so bar counts and month counts stay column-aligned.
- Both legends and the week-detail name chips are `Wrap`s; the gantt's month-label row and the month-card header use flexible children with ellipsis.
- Scroll body pads bottom ≥84px to clear the nav bar; the planner header and segmented control sit outside the scroll view, mirroring the Calendar screen.
- Every `CustomPaint` is wrapped in `Semantics` — a bare canvas is invisible to screen readers, and on these screens the canvas carries most of the information (`ganttRowSemantics`, `weekBarSemantics`).
- Dates for the week range and axis come from `intl` `DateFormat` with the active locale — never ARB, never `fmtDay`-style hand-built formatting.
